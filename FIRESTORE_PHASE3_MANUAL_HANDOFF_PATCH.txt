IzyTel Phase 3 - correctif affectation manuelle / ancien refus 9E

Cause confirmee
---------------
Une commande peut etre refusee dans un ancien cycle, puis reaffectee manuellement
plus tard. Supabase remet correctement son cycle `refused_agent_ids` a zero, mais
l'ancien miroir Firestore pouvait conserver :
- lastAssignmentRefusalReason
- lastAssignmentRefusedAt
- lastAssignmentRefusedAgentId
- autoAssignmentRefusedAgentIds

Le handoff Agent retombait alors sur l'ancien moteur 9E et pouvait refuser une
acceptation pourtant valide. Le message affiche sur la capacite etait trompeur.

Ce que fait le correctif
------------------------
1. Une affectation manuelle Phase 4 cree/repare maintenant immediatement un miroir
   Firestore minimal avant l'acceptation Agent.
2. La creation de ce miroir ne soustrait pas une seconde fois la reservation deja
   prise en compte par Phase 4/Supabase.
3. Une nouvelle affectation manuelle remet a zero les anciens champs de refus 9E
   dans Firestore. L'historique reste conserve dans orderAssignments/Phase 4 ;
   seul l'etat courant du nouveau cycle est nettoye.
4. Le refus d'un miroir manuel libere egalement Firestore afin que la reaffectation
   automatique suivante reste coherente.
5. Les regles Firestore autorisent ce miroir uniquement a Manager (role Firestore
   supervisor) et Admin. Agent et operator ne gagnent aucun droit.

Le script tools/phase3_patch_firestore_manual_handoff.ps1 modifie uniquement :
- isValidAdminManualAssignment(orderId)
- isValidManualAssignmentEventCreation()

Il sauvegarde d'abord les regles sous :
  firestore.rules.phase3-manual-handoff.bak

Execution obligatoire avant le test mobile :
  .\tools\phase3_patch_firestore_manual_handoff.ps1
  firebase deploy --only firestore:rules

Ne pas remplacer firestore.rules par un ancien fichier : le script corrige le
fichier actuellement present a la racine du projet.
