## Anomalies démontrées

1. **Élevée — deux registres critiques actifs.** `finances_page.dart:130` construit HybridFinanceOperationsRepository en production Supabase. Ce dernier délègue crédits, dépenses, Wave et clôtures à Firestore. Le BO utilise exclusivement RPC Supabase (`supabase_backoffice_finance_repository.dart`). `LegacyFinanceBackfillService.runIfNeeded` effectue une reprise unique ; SQL `20260915104403...` marque `firestore_bo5` terminé. Aucun flux continu de ces nouvelles écritures mobiles n'assure leur convergence après cette marque. Une dépense mobile post-backfill est absente du BO ; une dépense BO absente du mobile. Corriger avec adaptateur canonique ; conserver historique.
2. **Élevée — caisse BO calculée sur échantillon.** Dernière définition versionnée `20260915224305_bo5_finance_integrity_hardening.sql:4` limite commandes à 1000 et plusieurs flux à 500. `backoffice_finance_snapshot.dart:299-360` somme ces tableaux depuis ouverture pour produire le solde théorique. Les écritures sorties de fenêtre disparaissent du solde. L'historique par période (`20260917012401...`) ne corrige pas ce calcul, et limite lui-même à 2000. Fournir agrégats serveur indépendants de la pagination ; ne pas afficher somme bornée comme solde exhaustif.
3. **Élevée — idempotence dépenses absente.** RPC `izytel_finance_record_expense` (`20260915104335...:266`) génère UUID puis insert sans clé de commande ni unicité de référence. Rejouer une requête réseau réussie dont la réponse est perdue crée deux sorties. Les IDs Firestore de supplierPayments, creditSettlements et expenses sont aussi nouveaux par invocation (`firestore_finance_operations_repository.dart:506,703,766`). La transaction garantit l'atomicité d'une tentative, pas la déduplication entre tentatives.
4. **Élevée — clés BO instables entre tentatives.** `SupabaseBackofficeFinanceRepository.recordSupplierRecharge/Payment` crée `p_operation_key` avec DateTime.now().microsecondsSinceEpoch à chaque appel. Une réinvocation métier ne réemploie donc pas la clé d'origine ; une garantie RPC fondée sur celle-ci est inefficace pour ce retry. Le double clic peut être bloqué UI, mais cela ne constitue pas une garantie de serveur.
5. **Élevée — commissions V2 relisent Firestore.** `commission_v2_dashboard_page.dart:92` choisit FirestoreCommissionV2Repository. Celui-ci lit commissions/payouts/accounts exclusivement Firestore, alors que versements BO et registre Phase5 sont Supabase. Ces tableaux sont atteignables depuis les vues activité Agent/Admin. Un versement BO n'y apparaît pas sans synchronisation inverse inexistante dans ce repository.
6. **Moyenne — reprise miroir bornée.** `phase5_consolidated_synchronizer.dart` marque backfills complets puis reprend seulement 300 derniers flux et 1000 comptes. Après panne dépassant la fenêtre, une ancienne écriture miroir manquante peut rester absente. Les erreurs miroirs HybridFinance/HybridCommission sont journalisées après succès primaire, sans outbox persistante locale démontrée. Conserver mécanismes legacy ; proposer curseur/reprise durable après choix source.
7. **Moyenne — unicité règlement crédit fragile entre crédits.** `izytel_finance_settle_credit` verrouille le crédit puis fait EXISTS global référence sans index UNIQUE dans les SQL locaux. Deux crédits différents peuvent simultanément enregistrer la même référence. Sur le même crédit le verrou borne le total, mais retry retourne une erreur, pas résultat initial. Une contrainte d'unicité normalisée et clé métier sont nécessaires après examen historique des doublons.
8. **Non déterminé — socle SQL Phase5 non versionné.** Recherches dans tous SQL locaux : aucune définition des RPC phase5_record_supplier_recharge/payment/commission_payout, des CREATE TABLE phase5_*, ni de private.is_izytel_finance_admin/staff. Des migrations ultérieures référencent ces objets. Impossible d'attester RLS, validation identité/actif, unicité, verrouillage et intégrité de ces fondations sans export de schéma autorisé. Ne pas reconstruire les RPC par supposition.
9. **Moyenne — rapprochement mobile historique.** `firestore_financial_reconciliation_repository.dart:35-60` charge intégralement neuf collections Firestore ; union Supabase uniquement preuves/remboursements. Les nouveaux succès/commissions Supabase ne sont pas une source d'entrée ici. Diagnostic susceptible d'être incomplet ; conserver moteur et enrichir données canoniques.
10. **Moyenne — backfill transforme des valeurs invalides.** `20260915104403...` convertit certains montants <=0 en 1 et dates absentes en now(). Cela peut préserver la contrainte SQL mais altère un historique financier. Ne pas modifier données ; préférer signaler/quarantainer anomalies lors d'une reprise future validée.

## Protections à préserver

- Firestore finance est majoritairement Admin, écritures mouvements/dépenses/clôtures immuables ; getAfter/transactions vérifient plusieurs effets croisés.
- Supabase finance_* : RLS activée et droits directs anon/authenticated révoqués ; RPC SECURITY DEFINER search_path vide avec garde Admin pour écritures versionnées. Grants à anon ne signifient pas accès anonyme si garde JWT/registre est correcte ; dépendance garde absente du dépôt reste non vérifiée.
- Remboursement : dernière création WC6 verrouille commande, exige paiement confirmed, montant <= commande, rôle Admin ou Manager propriétaire de zone, dossier unique. Marquer payé exige approved et fait transition dossier + commande dans même transaction SQL ; second appel ne crée pas de deuxième mouvement mais lève erreur. Aucun paiement Wave réel n'est exécuté par cette RPC : elle enregistre une référence.
- Versement commission Firestore : identifiant dérivé référence normalisée + transaction compte/doublon ; conserver cette protection tant que legacy demeure.
- Formules locales sont regroupées dans finance_calculators.dart et network_finance_calculator.dart ; formule fixe commission 10 visible dans import finalisation, à rapprocher d'une règle commerciale approuvée non fournie.
